# 北大乒协比赛管理与公示系统

本项目用本地后台维护赛事、项目、分组、抽签和比分。页面代码与唯一的 JSON 数据库均在 `webpage/`，后台直接增量保存数据；整个目录可独立上传为静态公示站点。后台使用 Python 标准库，不需要安装额外 Python 包或 Node 包。

## 启动后台

项目已创建名为 `pkutta` 的 Conda 环境，其可移植包规格在 [`environment.txt`](environment.txt)。在本机项目根目录运行：

```powershell
conda activate pkutta
python -m backend.server
```

然后打开 <http://localhost:4000/>。后台只监听 `127.0.0.1:4000`，用于本机管理比赛数据。若在另一台电脑上安装，先运行 `conda create -n pkutta --file environment.txt`。

## 公示网页

将 **`webpage/` 目录中的全部内容** 同步到静态网站的发布目录即可；后续发布只需同步有变化的文件，无需运行 build。页面通过相对路径直接读取 `webpage/database/`，不依赖后台运行。本地预览使用 HTTP 服务：

```powershell
python -m http.server 8000 -d webpage
```

再打开 <http://localhost:8000/>。赛事、项目详情使用 `#` 路由，因此静态托管无需配置额外的重写规则。

后台右下角的 **Submit** 按钮会在 `webpage/` 独立 Git 仓库内依次执行 `git add .`、`git commit -m "automatic update"`、`git push origin master`。命令在后台执行，输出显示在启动后台的终端；运行时按钮灰色且不可重复点击，全部结束后恢复。成功保持安静，失败弹窗说明。没有新文件变化时仍可推送已有提交。无需 build。

## 数据与操作

数据按以下结构保存；每个阶段的 `metadata.json` 记录阶段类型、选手和种子级别，`data.json` 记录该阶段的抽签、场次与比分。后台和公开页共用这些文件，赛事及项目详情由页面读取对应的元数据和阶段数据，不再生成重复的汇总索引。

```text
webpage/
  index.html
  app.js
  style.css
  icon.jpg
  database/
    index.json
    <赛事英文名>/
      meta.json
      <性别>-<形式>/
        meta.json
        group|knockout|round_robin/
          metadata.json
          data.json
```

创建赛事时可勾选“自定义文件名”；文件名输入框始终显示，勾选后才可输入。文件名以小写英文字母开头，可含小写字母、数字和单个连字符，例如 `autumn-cup-2026`；不能带扩展名、路径或连续/末尾连字符，重复名会提示错误并保留原赛事。未勾选时自动生成 `competition-YYYYMMDD-随机编号`。创建后文件名不变。

创建项目时上传 CSV（UTF-8 或 GB18030），允许第一行是表头：单打为“选手姓名,队伍,种子级别”，双打为“选手1,选手2,队伍,种子级别”，团体为“队伍,种子级别,成员1,成员2,...”。种子级别可为 0 或正整数，数字越大优先级越高；独立淘汰赛的 CSV 还接受 `-1`，表示非种子且非小组第一的选手。小组赛与独立循环赛仍拒绝负级别，所有赛程都拒绝小于 `-1`。小组规格写作 `2*4(2) + 1*3(1)`，表示两个四人组各出线两人，以及一个三人组出线一人。淘汰赛轮数 `d` 允许出线人数位于 `(2^(d-1), 2^d]`，不足满额时自动补轮空。项目目录只使用 `<性别>-<形式>`，例如 `women-double`；浏览器地址为 `#/xsb26/women-double`。

小组赛和独立循环赛采用相同排名规则：胜一场积 1 分，负一场或双方弃权积 0 分。同分者仅比较彼此之间的比赛，依次按内部积分、局胜负比、球分胜负比排序，仍并列时抽签。后台保存各组或循环赛阶段的 `standings` 和 `ranking_draw_order`，刷新页面或修改计划不会重新抽签。比值精确比较，正数除以零视为无穷，`0/0` 视为零。旧的循环赛胜场、获胜局、总得分及姓名比较函数仅保留给兼容调用，页面排名使用新规则。

小组抽签先让级别最高的非零种子分别进入各组，额外种子与其他选手随机填充。淘汰赛所有正级别（包括 `1`）都属于种子，级别越高排名越前，签位按 ITTF 按排名设种规则：一号种子在上半区顶端（#1），二号种子在下半区底端（#2^d）；3–4 号抽入上半区底端和下半区顶端；5–8 号抽入奇数四分之一区的底端和偶数四分之一区的顶端；9–16 号对八分之一区同理，依此类推，直到每场首轮至多一名种子。例如 64 签时 3–4 号在 #32/#33，5–8 号在 #16/#17/#48/#49。`0` 表示非种子小组第一，随机进入没有种子的首轮场次，上半区占该场上方签位、下半区占下方签位，使签表上下镜像对称；`-1` 表示其他选手，与未安排的人一起随机填剩余位置，空位轮空。小签表使用能容纳的种子批次。已抽好的签表在后台重启或升级后保持原样，新规则只作用于此后的抽签和重新抽签。

小组出线后的级别由原报名正种子人数和小组数的较小值 `n_s` 决定：第 `g` 组第一名在 `g <= n_s` 时获得 `n_s + 1 - g`，其他组第一为 `0`，其余出线选手为 `-1`。出线人选不变而组内排名改变时更新级别并保留已有淘汰赛签表；主动重新抽签才使用新级别。

后台启动会按新规则重新计算旧项目的小组及独立循环赛排名，并同步小组后的淘汰赛出线元数据。资格人选相同则保留已有对阵和比分；新排名改变出线人选时清空旧淘汰赛签表，等待重新抽签。

后台场次详情中点击“添加一局”会增加临时空比分，逐行填写即可暂存，删除局数无需确认。每侧可输入整数或 `wo`（弃权），只填一侧 `wo` 时对侧空分自动补为 `0`；填写 `t` 局单方弃权得到 `t:wo` 大比分，对侧胜。双方弃权显示 `wo:wo`，允许标记完赛但没有晋级者，淘汰赛按轮空向后传播。单方弃权的负者仍可参加铜牌赛。排名计算局、球分时，所有 `wo` 视为 `0`。

点击“保存场次信息”会移除普通未完整填写的局，公开页也不展示这些临时局。普通完赛须至少有一局完整比分且胜局数不相等；单方、双方弃权也可明确标记完赛。规则实现位于独立的 [`backend/logic.py`](backend/logic.py)。

每个小组可设置预定时间、桌号和裁判，保存计划会覆盖本组所有场次的对应字段；修改单场实际信息不会改变小组计划，重新抽签保留计划。独立循环赛也可在卡片上统一设置预定时间、桌号和裁判，并单独修改各场的安排；单场修改不改变统一计划。所有弹出卡片仅通过卡片内按钮关闭。

小组赛和独立循环赛的选手表均不显示排名；全部场次完赛后新增排名表，按实际比较过程展示积分及所需的内部积分、局胜负比、球分胜负比、抽签名次列，未参与计算的单元格留空并为浅灰色。小组选手表和排名表高亮出线选手名字。前两张表宽度固定，排名表占剩余宽度并可横向滚动；未显示排名表时，前两表在电脑端整体居中。三表的表头统一为 43 像素、内容行统一为 46 像素，按排名表原有行高对齐。对阵单元格保留 56 像素列宽以容纳 `wo:wo`，完赛高亮整格；对称位置打开同一场次并按行列顺序显示比分。窄屏三表上下排列并居中，选手表固定 220 像素；过宽对阵图和排名表只在各自容器内横向滚动，页面宽度保持不变。淘汰赛叶子按签位显示 `#1`、`#2` 等编号。

每个阶段全部完赛后显示可收起的比赛结果卡片：小组赛展示出线名单，淘汰赛展示前八名，独立循环赛展示完整排名。结果表宽度不超过 580 像素并居中，选手姓名居中且可点开详情。作为项目最终结果的淘汰赛和循环赛，第一、二、三名的名次单元格分别使用黄色、银色、棕色背景。

每个项目的第一个阶段下方提供默认收起的“参赛名单”卡片，展开后以逗号分隔的段落显示原报名选手，点击姓名可查看学院。标题右侧的下载图标导出 CSV，保留上传时的单打、双打或团体列结构、报名顺序以及原报名种子级别，使用 UTF-8 BOM 和标准 CSV 引号规则以支持中文及含逗号的字段。导出使用前述标准表头，团体的成员表头数量取报名队伍中的最大成员数，可再次上传。

## 导航与搜索

顶部品牌和网页图标使用原样复制的 `vibecoding/Figure/icon.jpg`。顶栏固定在屏幕上方并带阴影，页面预留顶栏高度；点品牌返回首页。进入一个赛事或其项目页面后，右上搜索按钮可打开“搜索比赛场次”。输入成员姓名后点击搜索图案，查找本场赛事所有项目和阶段中选手 A 或 B 成员列表包含该姓名的场次；单打显示姓名、双打显示组合、团体显示队伍。结果列出项目·阶段、双方、状态及比分、预定时间桌号和裁判，未完成场次高亮。

380 像素及以下的窄屏顶栏只显示品牌图标，保留管理标识和搜索按钮；取消最小页面宽度以避免滚动条占位造成横向溢出。

页面按赛事信息、项目卡片和阶段内容逐块加载，等待或出错时保留已展示的标题、导航和内容。原始 JSON 与聚合后的详情在内存缓存 60 秒，相同的并发读取共用一个请求；同一项目在有效缓存期内切换小组赛/淘汰赛不重新请求。缓存过期时先保留已有内容，再更新对应块。后台保存后清理相关缓存，并阻止较早的请求覆盖新数据。搜索并行读取各项目，已经查到的结果会逐步显示；个别项目读取失败会单独提示，不丢弃其他结果。

## 开发与文档

`backend/storage.py` 负责输入校验、CSV 与 JSON 持久化，`backend/server.py` 提供本地 HTTP API，`backend/logic.py` 包含抽签、排名与淘汰赛递推逻辑，`backend/publish.py` 管理 Submit 后台任务。`webpage/` 保存共享页面代码和实时数据库。`generator/build.py` 仅保留旧调用的兼容检查入口：初始化旧数据库结构并检查页面文件，发布不需要调用。`docs/` 按相同相对路径提供文件说明，数据说明在对应 JSON 保存时更新。
